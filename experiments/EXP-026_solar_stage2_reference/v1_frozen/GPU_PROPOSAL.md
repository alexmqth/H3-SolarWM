# Conditional official Stage2 reference run — no GPU authorized in EXP-026/v1

This is a next-stage engineering proposal, **not an executed command or result**. The official fixed protocol is 158 RGB frames at 24 fps, 1344×768; 47 physical encoded video latents, 50 rollout latents, first 47 decoded, a separate image anchor, native camera view matrices and intrinsics, fixed noised silence audio, fused PRoPE camera attention, sliding-local student RoPE, W6 history, `cache_mode=exit`, video shift 12 and four denoiser evaluations per five-latent chunk. Evidence: `SolarWM/configs/examples/minimax_h3/infer-stage2-158f-sp4.yaml`, `src/solarwm/backends/minimax_h3/stage2.py`, `sgf.py`, `sgf_rollout.py` and `runtime.py` in official checkout `ce1da4e7705391eda8eeda6016c0fd3f614b975e`.

`h3_sgf_windows()` produces ten chunks. `h3_sgf_rollout()` makes four denoiser calls and one clean-cache commit call per chunk: **40 denoiser + 10 commit = 50 student transformer forwards** for one logical sample, before any additional condition encoding or VAE decode. Here “4 NFE” counts denoising calls per chunk; it does not count commit calls or total video forwards. This is a code-derived budget, not a measured runtime. GPU wall time and peak memory remain unmeasured.

The published example has world size 8 and SP4, hence logical DP2. `_validation_schedule()` rejects `sample_count=1` unless DP world size divides it. The candidate config uses SP8/DP1 solely to express one logical sample. However, `optional.load_transformer()` calls `.to(device)` on the complete transformer when `transformer_device_map: null`, and only then does `runtime.run_inference()` apply FSDP. The safetensors index reports 66,280,430,080 bytes = 61.73 GiB for the base transformer, exceeding a single L40's 46,068 MiB = 44.99 GiB before activations, LoRA, KV or codecs. Thus neither the published SP4/DP2 command nor this SP8/DP1 candidate is currently demonstrated to fit eight L40s. SP controls sequence parallelism; it does not solve this pre-wrap load.

Next-stage gates, in order:

1. Obtain accepted access to the official SolarWM-Data recipe and H3 latent generation, then download only the test index, two support files and one selected shard within an approved byte budget. Lock the seed-42 official candidate, full index row and hashes. Read its latent, caption/I0 and camera fields with the official reader on CPU. Never substitute an ABot/H3-World text-action sample.
2. Review and implement a separate, tested memory-safe load path (for example CPU load followed by per-rank FSDP sharding or an explicit supported device map). Verify base and EMA weight loading, SP/FSDP interaction, codec placement and CPU RAM/transfer cost before approving GPU inference. Do not infer feasibility merely from 8 cards existing.
3. Judge issues a new task version with a GPU budget and stop rule. Only then update the candidate and the fail-closed launcher with the verified memory preflight. A conditional invocation is `torchrun --standalone --nproc-per-node=8 -m solarwm infer --config <reviewed-single-case-config>` from the SolarWM checkout. This is **not** runnable under the current v1 authorization.

For an approved attempt, log per-rank phase times (load, condition/reader, first chunk, all ten chunks, commit, VAE decode, video write) and `torch.cuda.max_memory_allocated/reserved`, `nvidia-smi` device memory, CPU RSS and KV bytes. The stopping conditions must include load OOM, missing or mismatched sample contract, nonfinite latents, wrong 158-frame decode and the authorized time limit. No speedup or quality comparison with 832×480, 124-frame H3-World is valid without matching protocols.
